التحليل البرمجي لبناء نظام الخرائط الامتحانية مطابق للنظام المعروض في الفيديو
تحققت من الرابط المرسل، وهو يعرض نظاماً بعنوان «نظام الخرائط الامتحانية من مكتب الدائرة للحلول البرمجية»، وله موقع إلكتروني باسم نظام الخرائط الامتحانية.

الهدف هو بناء نظام مستقل يؤدي الوظائف نفسها، بدءاً من إدخال القاعات والأقسام والمراحل والطلبة، وصولاً إلى إنشاء الخرائط الامتحانية وتوزيع المقاعد وطباعة التقارير.

هناك فرق بين المطابقة الوظيفية بنسبة 100% ونسخ الشيفرة الأصلية: يمكن إعادة بناء الوظائف الظاهرة وتصميم واجهات مماثلة، لكن لا يمكن معرفة الخوارزميات أو قاعدة البيانات الأصلية بدقة من الفيديو وحده. لذلك سأميز بين الوظائف التي أمكن التحقق منها والتصميم البرمجي المقترح لتنفيذها.

القواعد الرياضية الأساسية:
\[
\sum_s x_{i,s}=1
\]

كل طالب مؤهل يحصل على مقعد واحد بالضبط.
\[
\sum_i x_{i,s}\leq 1
\]

لا يسمح بجلوس أكثر من طالب على المقعد نفسه في الفترة الامتحانية.

حيث \(x_{i,s}=1\) إذا خُصص المقعد \(s\) للطالب \(i\)، وصفر خلاف ذلك.

يمكن إضافة دالة هدف تقلل تجاور طلبة المادة نفسها، وتقلل فتح القاعات الاحتياطية، وتراعي الاحتياجات الخاصة.

مثال عملي: إذا كانت القاعات 101 و102 و103 تتسع كل منها لـ30 طالباً، وكانت القاعة 103 احتياطية، فإن توزيع 47 طالباً يحتاج قاعتين فقط، بينما توزيع 74 طالباً يحتاج القاعة الثالثة أيضاً. هذا بافتراض إمكان استخدام المقاعد الثلاثين كلها.
5. برمجة إدارة المراقبين
إدارة المراقبين ليست مجرد قائمة أسماء؛ بل هي نظام توزيع وظيفي مرتبط بمواعيد الامتحانات.

ينبغي حفظ بيانات كل مراقب مثل الاسم، اللقب العلمي، القسم، نوع التكليف، مدى التفرغ، الأيام المستثناة وعدد المراقبات السابقة.
قواعد التوزيع
1. لا يُكلَّف المراقب بقاعتين في الوقت نفسه.
2. يخصص لكل قاعة عدد المراقبين المطلوب حسب قاعدة تحددها إدارة الكلية.
3. يراعى عدم تكليف المراقب في أيام عدم توفره.
4. يوزع عبء المراقبات بعدالة قدر الإمكان.
5. يمنع التكليف أثناء وجود التزام رسمي آخر مسجل.
6. يمكن إسناد مراقب بديل عند الغياب، مع الاحتفاظ بسجل التغيير.
لتحقيق العدالة، يمكن استخدام دالة هدف تقلل تفاوت أعباء المراقبة:
\[
\min \sum_{j=1}^{m}(L_j-\bar L)^2
\]

حيث \(L_j\) يمثل عبء المراقبات المسند إلى المراقب \(j\)، و\(\bar L\) متوسط عبء المراقبات المستهدف. ويمكن وزن المراقبات بحسب مدتها، لا عددها فقط.

CREATE TABLE seating_assignments (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    period_id BIGINT UNSIGNED NOT NULL,
    student_id BIGINT UNSIGNED NOT NULL,
    seat_id BIGINT UNSIGNED NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uq_student_period
        UNIQUE (period_id, student_id),

    CONSTRAINT uq_seat_period
        UNIQUE (period_id, seat_id),

    FOREIGN KEY (period_id) REFERENCES exam_periods(id),
    FOREIGN KEY (student_id) REFERENCES students(id),
    FOREIGN KEY (seat_id) REFERENCES room_seats(id)
);

مثال على حفظ التوزيع بشكل آمن

DB::transaction(function () use ($periodId) {

    $period = ExamPeriod::whereKey($periodId)
        ->lockForUpdate()
        ->firstOrFail();

    if ($period->status !== 'draft') {
        abort(409, 'الخريطة معتمدة ولا يمكن تعديلها');
    }

    $candidates = ExamCandidate::where(
        'period_id', $periodId
    )->get();

    $availableSeats = RoomSeat::query()
        ->where('is_active', true)
        ->whereHas('room', function ($q) {
            $q->where('is_active', true);
        })
        ->get();

    // يتحقق المحرك من أهلية الطلبة،
    // وتوفر القاعات والتعارضات والقيود.
    $solution = app(SeatingSolver::class)
        ->solve($period, $candidates, $availableSeats);

    foreach ($solution as $assignment) {
        SeatingAssignment::create([
            'period_id' => $periodId,
            'student_id' => $assignment['student_id'],
            'seat_id' => $assignment['seat_id']
        ]);
    }
});



هذا مثال لبنية خدمة الحفظ، وليس محرك التوزيع مكتمل التنفيذ. يجب أن تعيد دالة solve() حلاً صالحاً أو خطأ واضحاً عندما يستحيل التوزيع، مع اعتماد قيود قاعدة البيانات لضمان عدم التكرار.

11. ما الذي أضيفه ليكون مناسباً للكليات العراقية؟
عند بناء النظام للكلية التقنية بعقوبة مثلاً، أوصي بإضافة دعم النظام الفصلي ومسار بولونيا، مع التمييز بين الدراسة الصباحية والمسائية، وشعب الطلبة، والطلبة المحملين بالمواد، وامتحانات الدور الأول والثاني.

وأرى ضرورة إنشاء ثلاث واجهات مستقلة: واجهة الإدارة الامتحانية، واجهة التدريسيين والمراقبين، وواجهة الطلبة. كما ينبغي أن يكون من الممكن تشغيل النظام داخل الشبكة المحلية دون إنترنت، مع إمكانية نشر بوابة الطالب خارج الشبكة عند الحاجة.
الخلاصة الهندسية
لإنتاج نظام مشابه للفيديو، يتعين بناء عشر وحدات وظيفية متكاملة، مع ثلاثة محركات رئيسية: محرك توزيع الطلبة، ومحرك توزيع المراقبين، ومحرك توليد الخرائط والتقارير.

أوصي ببناء النظام باستخدام PHP وLaravel وMySQL، مع محرك توزيع قائم على القيود، وليس على الاختيار العشوائي البسيط. ولا أرى حاجة إلى الذكاء الاصطناعي لتنفيذ التوزيع الأساسي؛ فالخوارزميات الرياضية وقيود قاعدة البيانات أكثر قابلية للتحقق والتدقيق في هذه المهمة.

يمكن تحقيق تطابق وظيفي شامل مع الأجزاء المعروضة من النظام، لكن إثبات مطابقة بنسبة 100% يستلزم مقارنة تفصيلية لكل شاشة وسلوك وتقرير مع النسخة الأصلية، بما في ذلك الوظائف غير المعروضة في الفيديو.
